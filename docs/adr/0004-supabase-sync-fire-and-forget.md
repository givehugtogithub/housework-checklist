# Supabase 寫入採 fire-and-forget，失敗只記錄不重試

`createStore` 的每個變動方法（`click`/`addChore`/`removeChore`/`renameChore`）在有注入 adapter 時，會同步觸發對應的 Supabase 寫入呼叫，但不 await、不重試，失敗只 `console.error`。畫面上的變動一律是本地樂觀更新（store 記憶體內的狀態），使用者不會等待網路往返，也不會看到寫入失敗的提示。這是刻意為兩人小工具做的簡化：「非即時」的需求本來就只要求重新整理／換裝置能讀到最新資料，不要求每一步寫入都有可靠性保證或即時回饋；真正的即時同步/可靠性留給 ENG-4 視需要處理。

另外，`cells` 表用 Postgres 原生 `date` 型別存日期，而不是只存 `day`，是因為月曆表現在可以切換月份（見 CONTEXT.md 月曆表定義）——如果只存 `day`，換月之後同一個 `(chore, day)` 會撞名，悄悄覆蓋掉其他月份的紀錄。RLS 政策則對 `anon` 角色完全開放（無列過濾），因為這個 app 從頭到尾只服務 Sean/Vera 共用的一份資料，沒有登入、沒有多租戶，呼應 ADR-0001 已經接受的「anon key 公開內嵌，靠 RLS 限制讀寫範圍」原則。

## Consequences

- 寫入失敗時使用者不會馬上發現，要等到重新整理或另一台裝置看到資料沒同步才會注意到；之後若要加可靠性保證（重試、離線佇列、失敗提示），需要另外設計，現有的 fire-and-forget 呼叫點都要重新檢視。
- RLS 政策本身不會擋下任何用 anon key 發出的請求；資料保護完全依賴「這個網址/key 沒有外流」。之後若要加多租戶或權限控管，這個政策要整個重寫，不是加一條規則就能解決。
